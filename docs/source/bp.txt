1. Executive build directive
Build a complete rental-equipment operations application that connects equipment, customers, rentals, inspection evidence, damage assessment, maintenance work, repair-charge approval and S/4HANA billing status into one traceable lifecycle. Deliver working source code and reproducible local run steps—not only wireframes, generated files, or a plan.

3. Findings, conflicts and required corrections
Finding
Why it matters
Blueprint resolution
S/4HANA vs SAP HANA wording
S/4 business objects must be changed through supported business APIs; writing to the S/4 database schema can bypass business rules and is not an accepted integration contract.
CAP owns operational records in its app database. Use S/4 APIs via Destination/Connectivity for S/4 business operations. Do not issue SQL against S/4 application tables.
Local master data vs S/4 source of truth
FR-001 says users maintain customers, while INT-02 says customers sync from S/4. Similar ambiguity exists for rentals/contracts.
Implement adapters and a configurable source-of-truth policy. Demo mode allows local CRUD; S/4 read-through mode treats synchronized customers as read-only; production write-through is enabled only after the business API/process is agreed.
Two media platforms named
FRD names Cloudinary for photos/PDFs and SAP Object Store with S3-compatible API for photos/video. Duplicating evidence is a cost, integrity and retention risk.
Use one authoritative private object-storage provider through `MediaStorageProvider`. Default to S3-compatible Object Store. Keep DIM/doc repository as a separate optional `DocumentRepositoryProvider`; do not add Cloudinary unless explicitly selected.
Billing API ambiguous
FRD lists `API_DEBIT_MEMO_REQUEST_SRV` or `API_SALES_ORDER_SRV`; standard billing document read API is not necessarily the API used to create the source document.
Isolate billing behind `BillingPostingProvider`. Verify API and business process against target S/4 edition/release and Finance decision. In demo mode return clearly marked simulated document IDs.
Maintenance API name/version may differ
FRD labels a maintenance notification API; SAP publishes versioned API names and may use OData V2 or V4 by edition/release.
Verify target metadata and use the exact supported API. Do not hardcode the FRD alias as a guaranteed endpoint. Capture verified base paths, entity sets, auth and version in `docs/integrations/s4-api-matrix.md`.
Location transfer is required but not modelled
FR-011 requires a transfer history, while the ERD stores only current Equipment.LocationID.
Add append-only `EquipmentLocationHistory` with from/to location, transfer timestamp, actor, reason, source and sync key. Update equipment current location in the same transaction.
Audit/outbox/sync state absent from ERD
Mandatory offline operation, retries, audit, immutable evidence and integration replay cannot be safely represented by the ten entities alone.
Add AuditEvents, IntegrationOutbox, IntegrationSyncRuns, IdempotencyRecords, MediaAssets/Metadata and checklist/configuration tables.
Damage compared with checkout baseline
FRD says new damage must be billed and pre-existing damage must not; the ERD does not represent baseline comparison.
Link check-in condition log to checkout condition log/item and require a human-confirmed `NewDamageComparedToCheckout`/liability decision with evidence before a charge can be posted.
Photo binary in the database conflicts with object store
LargeBinary per photo can bloat HANA and undermine lifecycle/versioning.
Store bytes in private object storage; keep only metadata, provider/key, checksum, MIME, byte size, captured/uploaded times and uploader in HANA.
Unknown currency, tax and approval threshold
Amounts are decimal, but business currency, tax regime, rate inclusivity and auto-approval threshold are not approved.
Use ISO currency code per monetary transaction, configurable tax provider/rules, decimal minor-unit rounding, and configuration tables. Until a threshold is configured, fail closed: route charges to manual approval.
“Automatic” cannot mean unreviewed photo-based billing
Image AI is explicitly out of scope; photo capture alone cannot prove customer liability.
No AI damage inference. Human inspector records damage and liability; compare history; apply configurable charge and approval rules; log reason and evidence. Auto-post only after required approval conditions are satisfied.
KPI claims need operational measurement
95% billed damage, <15-minute auto billing, <24-hour approvals are outcomes, not guaranteed code features.
Implement timestamps, status events and dashboard measures so they can be measured; never fabricate target achievement in seed data or the go-live report.

5. Functional scope and role workflows
5.1 Release 1 scope
Build everything within the supplied Release 1 boundary: equipment tracking, rentals/items, checkout/check-in inspection, damage records/photos, liability/repair estimate, maintenance, repair charge approval and S/4 integration abstractions, reports, location transfer, audit, outbox and offline mobile workflow. Keep AI photo damage detection, IoT/telematics and customer self-service explicitly out of scope.

5.3 Primary end-to-end journeys
Fleet overview → search/filter asset → open asset detail → view status, location, active rental, next maintenance and complete timeline.
Checkout: scan equipment → confirm it is assigned to the correct rental item → complete checklist → record meter/grade/photos/signature → mark item checked out only after validation.
Return: scan equipment → load checkout baseline → checklist and mandatory views/photos → compare baseline to return state → create damage records only where inspector confirms new damage → set liability to pending review if uncertain.
Charge: damage estimate → finance policy and tax calculation → approval routing → create idempotent outbox command → verified S/4 business API adapter → persist external request/document IDs and polling status.
Repair: create maintenance notification/order if configured and approved → assign technician → capture work and actuals → release equipment only after required inspection and role validation.
Location transfer: scan asset → verify permissions and target location → append transfer history → update current equipment location atomically → sync S/4 only if ownership/API contract requires it.
Offline: locally save inspection and evidence manifest with device-generated IDs → display pending sync → retry safely → reconcile server response → never duplicate inspections/damages/billing after replay.
Outage: continue allowed offline inspections; queue outbound events; surface integration outage and queue age; retry and reconcile after recovery; never report success before SAP confirms it.

7. Business rules and state machines
7.1 Rental and equipment lifecycle
Rental: DRAFT → BOOKED → CHECKED_OUT → PARTIALLY_RETURNED → RETURNED → CLOSED
Optional terminal states: CANCELLED. OVERDUE is derived from the expected return date and open items, not a status trusted from the client.
Equipment: AVAILABLE → RESERVED → RENTED_OUT → INSPECTION_PENDING → AVAILABLE
Damage path: INSPECTION_PENDING → QUARANTINED/DAMAGED → IN_REPAIR → INSPECTION_PENDING → AVAILABLE
Other terminal/administrative state: RETIRED. All transitions occur through named CAP actions.
Agent must implement transition maps and unit tests; generic PATCH must not permit a caller to jump directly between arbitrary statuses. Each transition verifies role, plant scope, relevant associated records and reason when it is an override.
7.2 Condition grade
Grade
Proposed interpretation
Default behavior
A
Excellent / no material issues.
May release to available if inspection complete and no open safety damage.
B
Good / expected wear.
Release may be allowed by checklist rules.
C
Fair / defect or repair may be needed.

These are starting labels only; business owners must approve the exact meaning, translations and release rules. Do not infer condition grade from photos; grade is human-entered, validated and audit logged.
7.3 Damage, customer liability and evidence rules
Every damage record must reference the inspection that observed it. A check-in damage claim should reference or compare against the relevant check-out baseline for the same rental item/equipment.
Use explicit states for liability: PENDING_REVIEW, CUSTOMER_LIABLE, NOT_CUSTOMER_LIABLE, DISPUTED, WAIVED. Keep the original assessor, reviewer, timestamp, reason and evidence link.
Before billing, require documented confirmation that the damage is new relative to baseline, photos satisfy the configured requirement, repair scope/estimate exists, charge currency is known and a valid rate/tax configuration was applied.
Keep the photo bytes private and immutable after submission; corrections/additional evidence should add a new media version/record rather than silently replacing the original. Compute SHA-256 server-side when uploaded and verify on retrieval/processing where supported.
No AI-based damage detection is to be built in Release 1. The UI may present evidence comparison but cannot automatically conclude customer liability.
7.4 Pricing and billing calculation
repairSubtotal = approved parts + approved labor + other allowed charges
taxAmount = taxProvider.calculate(repairSubtotal, configuredTaxContext)
totalAmount = roundCurrency(repairSubtotal + taxAmount, currency)
Never trust amounts sent by a browser/mobile client. Calculate and persist the rule/version snapshot server-side.
A bill is eligible to post only when: damage is chargeable + evidence is complete + liability is approved
+ no conflicting posted charge exists + approval policy is satisfied + billing adapter is configured.
Rental total should be derived from item rate snapshots and an approved day-count convention (for example, inclusive/exclusive end date), discount/late-fee policy, and currency. The FRD does not define the convention; implement it as a tested policy function and record the chosen rule on the rental. Never assume tax rate, tax-inclusion, currency, loss-of-use fee or ledger account.
7.5 Billing states
DRAFT → PENDING_APPROVAL → APPROVED → POSTING_PENDING → POSTED
Transitions from PENDING_APPROVAL may also go to ADJUSTMENT_REQUIRED, REJECTED, DISPUTED or WAIVED.
POSTING_PENDING → POSTED on confirmed S/4 response/reconciliation; → POSTING_FAILED on non-retryable error; transient errors remain retryable.
Retry after timeout must reuse the same idempotency/business reference and reconcile S/4 before creating a new request.

8.1 Required API behavior
Use OData V4 conventions and CAP-generated metadata for back-office data services. Verify `$count`, `$skip`, `$top`, search and paging in the actual generated service.
Use structured validation errors with stable error codes and correlation IDs. UI should show human-readable reason, not raw stack traces.
Add correlation ID on each request and propagate to outbox/SAP calls/logs. Mask personal data and secrets in logs.
Use ETags/optimistic concurrency for mutable records where supported, especially approvals/configuration. Return a conflict instead of silently overwriting concurrent work.
Paginate all high-volume collections; do not load all assets or media into memory. Use indexes, server-side filtering and bounded payload sizes.
Document all status transitions and actions; generic CRUD must not bypass business rules.

10.2 Offline data and synchronization
Concern
Required implementation
Local persistence
Encrypted SQL store for drafts, inspection payloads, checklist versions, sync metadata and media file references. Avoid unencrypted photo/database cache on shared devices. Store credentials/tokens in platform secure storage.
Stable identifiers
Generate UUIDs on device before sending. Each operation includes `deviceId`, `clientOperationId`, idempotency key, entity IDs, client createdAt, payload schema version and local sequence.
Append-only inspections
Submitted inspections and initial evidence are immutable. Corrections become correction records/events. Device replay must not create a new inspection if the operation was already acknowledged.
Sync protocol
Pull reference/config versions with cursor; push bounded batches; server validates per operation; return per-item ACCEPTED/REJECTED/CONFLICT plus server IDs/cursors.
Conflict rules
Reference/master records: server authoritative. Inspection evidence: append-only merge where valid. Equipment current status/location: server workflow wins and app asks user to resolve stale state. Bills/postings: server only.
Retry policy
Retry network/transient errors with exponential backoff and jitter. Do not retry validation/authorization failures automatically. Preserve failed payload safely for debugging with data masking.
Media upload
Persist encrypted local file and metadata; use short-lived upload URL/session; verify bytes/checksum server-side; acknowledge upload separately from inspection sync; resume/retry uploads without duplicating media records.
Retention and logout
Clear tokens and local protected data according to MDM policy; protect unsynced records from accidental loss and inform the user. Implement remote wipe as an integration hook if mobile-management services are provisioned.

11.3 Sync and outbox mechanics
Run scheduled reference synchronization at a configurable 15-minute interval and allow an authorized on-demand sync. Keep checkpoints/watermarks, last successful run, fetched/upserted/skipped counts and errors.
For a business write, validate and commit the CAP business record plus outbox message in the same local database transaction. A worker claims queued messages using a concurrency-safe lease/lock and sends them to the adapter.
Persist request correlation/reference before/with the external attempt. Use a stable idempotency key based on business operation; when S/4 does not support idempotency keys, query/reconcile by external reference before issuing a second create.
Classify errors: retry transient network/429/5xx/timeouts; require intervention for validation, permission, configuration and business-rule errors. Use exponential backoff + jitter, max retry policy, then DEAD_LETTER with alert. Do not drop payloads.
On ambiguous timeout during a create, do not blindly create again. Reconcile via external reference/document lookup, then mark success or keep an explicit ambiguous state for manual resolution.
Mask sensitive payload properties from UI/logs. Integration Monitor retries require permission and create audit events; replay cannot edit original business facts.
Use Event Mesh only if provisioned and confirmed; polling fallback must be supported for billing-status readback.
